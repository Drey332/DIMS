This solution uses a lightweight stack (e.g. Python with FastAPI or Node.js with Express) for ease of deployment. FastAPI is an excellent choice for a quick, high-performance API in Python

Backend API Design
We design a RESTful API with clear endpoints to serve the scenario data. The backend will be responsible for returning all scenarios, filtering scenarios by keyword, and returning a specific scenario by ID. We will also implement basic logging for search queries (e.g., log each query string and timestamp for auditing). Below are the endpoints and their behavior:
GET /scenarios – Returns all emergency scenarios as a JSON array.
GET /scenarios?q=<keyword> – Returns filtered scenarios whose title or content matches the given keyword (case-insensitive substring match).
GET /scenarios/<id> – Returns the single scenario with the given ID (e.g. scenario ID “3” for Collision).
Each scenario object includes at least an id, title, and procedure (content). For consistency, we use a numeric or short string ID for each scenario. For example, a response from /scenarios might look like:

Implementation with FastAPI (Python)

from fastapi import FastAPI, HTTPException
import logging

# Initialize app and logger
app = FastAPI()
logging.basicConfig(filename="queries.log", level=logging.INFO, format="%(asctime)s - %(message)s")

# In-memory scenario data (id, title, procedure)
scenarios = [
    {"id": 1, "title": "Serious Illness, Injury or Fatality", 
     "procedure": "If an injured person must be recovered on deck, use the approved stretcher (Stokes Stretcher)...:contentReference[oaicite:22]{index=22}"},
    {"id": 2, "title": "Fire Onboard Vessel", 
     "procedure": "Fire onboard a vessel is one of the most life-threatening emergencies. Immediately sound the alarm, assemble fire-fighting teams...:contentReference[oaicite:23]{index=23}"},
    {"id": 3, "title": "Collision with Vessel/Structure", 
     "procedure": "In a collision incident, assess damage and take on water status. Muster all crew and prepare to send distress call..."},
    # ... (other scenarios extracted from ERP documents)
]

@app.get("/scenarios")
def get_scenarios(q: str = None):
    """Return all scenarios, or filter by keyword if q is provided."""
    # Log the query for auditing
    query_str = q or "ALL"
    logging.info(f"Search query: {query_str}")
    if not q:
        return scenarios  # return all scenarios
    # Filter scenarios by keyword in title or procedure (case-insensitive)
    keyword = q.lower()
    results = [s for s in scenarios if keyword in s["title"].lower() or keyword in s["procedure"].lower()]
    return results

@app.get("/scenarios/{scenario_id}")
def get_scenario_by_id(scenario_id: int):
    """Return a single scenario by ID."""
    for s in scenarios:
        if s["id"] == scenario_id:
            return s
    # If not found, raise 404
    raise HTTPException(status_code=404, detail="Scenario not found")
This FastAPI code defines the required endpoints. The search filtering simply checks if the keyword appears in the title or procedure text. For example, a request to /scenarios?q=fire will return the Fire Onboard scenario (and any others mentioning “fire”). The query parameter q is optional; if omitted, all scenarios are returned
fastapi.tiangolo.com
. FastAPI automatically serializes Python lists/dicts to JSON, so returning scenarios yields a JSON array of scenario objects. We’ve also included basic file logging: each search query (including “ALL” for full lists) is recorded with a timestamp in queries.log for audit purposes. Note: If using Express/Node.js, the implementation is similar: define routes for /scenarios and /scenarios/:id, use req.query.q for the keyword, and filter an array of scenario objects. Frontend Search UI Implementation
The search UI will be a simple web interface allowing users to input keywords and view matching scenarios. The design should be clear, intuitive, and responsive, appropriate for offshore safety personnel (meaning it should be easy to read on various devices and in potentially high-stress situations). Key elements of the UI:
Search Bar: an input field where users enter keywords (e.g., “fire”, “medical”, “diver”).
Results List: a section that displays each matching scenario’s title and brief content snippet or full procedure. Each result should be clearly separated and labeled with its scenario ID and title, followed by the procedure details. If many scenarios are returned, they could be collapsible or truncated for easier browsing.
No Results Indicator: if no scenario matches the query, the UI should clearly say “No matching scenarios found.”
Ask AI Button (Optional): An optional feature could be an “💡 Ask AI” button or section. If integrated with an AI service (like OpenAI’s API), users could select a scenario or enter a follow-up question (e.g., “What should I do first if there’s a fire?”), and the system would use the scenario content plus the question to get an AI-generated answer. This is an enhancement for interactive guidance, but the core system should function without it if not configured.
To implement the UI, we can use HTML5, CSS (or a framework like Bootstrap), and JavaScript. The UI does not need a heavy framework; a simple static page that calls the API is sufficient. We ensure it is mobile-responsive (using either CSS flexbox/grid or Bootstrap classes) and has a clean look (e.g., large legible text, clear headings for each scenario). Example HTML Structure:

Deployment Considerations
Both the backend and frontend are lightweight and easy to deploy. For FastAPI, we can run with Uvicorn (ASGI server) for production: e.g. uvicorn main:app --host 0.0.0.0 --port 80. The code is self-contained (no external DB required in demo mode), and can be containerized with a simple Dockerfile if needed. Similarly, an Express app can be run with Node and easily containerized. Static files (the HTML/JS for the UI) can be served by the same backend (using FastAPI’s StaticFiles or Express’ static middleware), or by any web server. The solution’s design emphasizes clarity and speed. By using FastAPI, we leverage automatic documentation (OpenAPI docs at /docs) and high performance for concurrent requests
fastapi.tiangolo.com
. By keeping data in memory (or using a simple JSON store), the search is extremely fast given the limited number of scenarios. This is easily extensible to a database like MongoDB or PostgreSQL if needed: the API could query the DB instead of a list, but the external interface remains the same. The UI being static means it can even be served from a file system or CDN, querying the API via AJAX. Finally, the Ask AI integration can be implemented by adding an endpoint that uses an OpenAI SDK to send the user’s question and the relevant scenario text to a model (like GPT-4) and returns the answer. This requires API keys and careful prompt design (possibly out of scope for now), so we’ve kept it optional. The button is there to illustrate how it could be hooked up.
Conclusion
We have built a comprehensive HydroSafe ERP scenario search tool comprising a backend API and a front-end UI. Users can quickly search emergency scenarios (like fire, man overboard, medical emergencies) and see the official procedure from the ERP on how to respond. The API endpoints (/scenarios, /scenarios?q=, /scenarios/<id>) provide structured data for all scenarios, search results, or specific scenarios, respectively. The web UI provides a user-friendly portal to query this information on any device, with clear presentation of titles, IDs, and procedures. Optional AI-powered Q&A can further enhance the tool by allowing natural language questions. This solution is built on lightweight, deployable technology, ensuring it can be readily adopted on offshore sites for improving safety responses. By combining the authoritative ERP document content with modern search functionality, HydroSafe personnel can access critical emergency guidance in seconds, which is invaluable in time-sensitive situations.
